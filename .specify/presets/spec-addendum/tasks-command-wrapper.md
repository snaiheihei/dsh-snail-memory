## 行为任务：测试与实现同一闭环

> preset 注入，优先于下文。下文“Tests are OPTIONAL”与独立测试任务示例由本节替代。

- 每个改变可观察行为的任务，都必须对应 `spec.md` 的至少一条验收标准，并在同一个复选框内包含测试与实现。
- 任务描述必须同时给出测试文件和实现文件的准确路径，明确要验证的行为；不要只写“添加测试”或“实现功能”。
- 一个任务只覆盖一个可独立验证的行为。包含多个独立行为时拆成多个任务，每个任务各自走一轮红→绿→重构。
- 不设置按用户故事集中排列的测试小节，不生成独立测试任务复选框。测试是行为任务的红灯步骤，不能脱离实现单独勾选完成。
- 纯配置、纯文档、纯静态资源和环境准备任务不包含红灯步骤，任务描述注明“无行为变更”。
- 保留下文的任务 ID、`[P]`、`[US*]`、依赖顺序和文件路径规则。`[P]` 只用于文件与依赖均不冲突的任务。
- 省略没有任务的阶段和模板尾注；任务只写验收映射、准确路径和待验证行为，不复述 plan.md 的算法或研究结论。
- plan 或 research 为某项实现引用了 REF-ID 时，在对应任务中保留该 ID，供 implement 回读 `references.md` 的单一索引条目；无关任务不添加参考，不复制参考正文。

示例：

```text
- [ ] T012 [US1] 在 tests/auth.test.ts 验证登录失败限流，并在 src/auth.ts 完成最小实现与重构
- [ ] T013 配置 CI 测试任务（无行为变更），修改 .github/workflows/ci.yml
```

判据：每个行为任务都能独立执行“先红、后绿、再重构”，不存在需要另行寻找对应实现任务的测试复选框。
