# 技术选型门禁

`/speckit-plan` 的 `before_plan` 强制钩子。作用：把选型摆到用户面前，让他拍板，再生成任何 plan 文档。

## Step 0 · 固定 feature，复用有效决策

显式 `SPECIFY_FEATURE_DIRECTORY` 与 `.specify/feature.json` 的 `feature_directory` 不一致时停止，不写任何文件。

当前 feature 的 `tech-decisions.md` 已含用户确认原话和确认时间，且用户未要求重新选型时，报告“沿用现有技术决策”并直接回到 plan；不重复候选表，不改写决策文件。

## Step 1 · 判定项目类型

**旧项目**（命中任一）：项目根有依赖清单或锁文件（`package.json` / `pyproject.toml` / `requirements.txt` /
`go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle` / `*.csproj`）；或已有成规模业务源码。

**新项目**：其余情况。`specs/` 下只有规格、还没代码的，按新项目算。
拿不准时问一次，不要反复确认。

这里的"环境"指**项目现有技术栈**，不是本机装了什么。

## Step 1.5 · 读取相关参考

当前 feature 存在 `references.md` 时，只读取标记 `plan` 且与本次选型相关的条目；需要核实候选能力时再回读对应原材料。参考方案只作为候选或证据，不直接获胜，也不替代每域至少两个候选、五维比较和用户拍板；无法核实的优势标“未验证”。

有效技术决策按 Step 0 直接复用。新增参考需要改变既有选型时，必须由用户明确要求重新选型，不因 references.md 更新而静默改写决策。

## Step 2 · 选型

**新项目（产品优先）**：本机已装环境不参与选型，缺 SDK 或缺依赖都不构成排除理由。每域 ≥2 个候选，
按五维打分（1–5，分高者优；实现难度按**易实现程度**折算；美观只在 UI 域计分，其他域标 `—`）：

| 维度 | 判据 |
|---|---|
| 实现难度 | 概念数、代码量、需自建的基础设施量 |
| 可扩展性 | 加一类对象/页面/集成时，改动是否局部 |
| 美观 | 默认产出能否直接达到可交付设计水准 |
| 主流程度 | 社区活跃度、近 24 个月发布节奏、文档密度 |
| 现代化 | 是否当前默认选择、是否仍在演进、是否已淘汰 |

**旧项目（环境优先）**：沿用现有栈；同一职责只有一个框架；新依赖先问"现有栈为什么做不到"；
迁移写成独立提案。五维只用于比较栈内部的实现方式。

## Step 3 · 输出并停止

按下面结构输出，**然后结束本轮等用户回复**：

```markdown
## 技术选型待拍板
**模式**：新项目（产品优先） / 旧项目（环境优先）　**依据**：<命中哪条信号>

### <技术域>
| 候选 | 实现难度 | 可扩展 | 美观 | 主流 | 现代化 | 总分 | 取舍 |

### 推荐方案
- <域>：<候选> —— <一句理由>

### 需要你决定
- 全部按推荐 → 「确认」　- 改某域 → 指出域和候选　- 都不满意 → 给约束，我重出

### 这会带来的安装项（交付物，不是选型依据）
- <SDK / 运行时 / 服务> <版本>
```

只改被质疑的域，其余保留。用户拍板前不写任何文件。

## Step 4 · 写 tech-decisions.md

写到 `specs/<feature>/tech-decisions.md`（feature 目录取自 `.specify/feature.json`）：

```markdown
# 技术选型决策（已拍板）

**模式**：<...>　**判定依据**：<...>
**确认时间**：<ISO-8601>　**用户确认原话**：<逐字摘录>
**相对推荐方案的改动**：<无 / 域 X 从 A 改为 B>

## 决策表
| 技术域 | 选定 | 与现状的关系 | 五维得分 | 一句话依据 | 放弃的候选 |

## 候选对比（供后续复盘）
<各域完整打分表>

## 环境准备清单
- [ ] <SDK / 运行时 / 服务> <版本> —— 用途

## 是否升级为 ADR
<见 Step 4.5；没命中写"无">
```

## Step 4.5 · 判定哪些决策升级为 ADR

三条全中才写，缺一不写：**难逆**（改主意成本实打实）、**不解释会困惑**（后人看到会问为什么）、
**有真实取舍**（存在其他合理方案）。

命中典型：架构形态、跨模块集成方式、带锁定的选型（数据库/消息队列/部署目标）、边界与所有权划分、
刻意的反直觉选择、代码里看不见的约束（合规、合作方 SLA）。

命中则写 `docs/adr/NNNN-<slug>.md`（编号取最大值 +1），一段话即可：

```markdown
# <决策标题>

<1–3 句：背景、决定了什么、为什么。>
```

可选段落（Status / Considered Options / Consequences）只在这三样真有价值时加。写完在
`tech-decisions.md` 里列出编号与一行理由。

## Step 5 · 回到 plan

写完直接继续被中断的 `/speckit-plan`，不再问是否继续。plan 只消费这份文件：`research.md` 引用结论，
`plan.md` 的 Technical Context 照填。

## Done When

- [ ] 有效决策已复用，或新模式与判定依据已声明
- [ ] 新选型时每域 ≥2 候选 + 五维打分，用户明确拍板
- [ ] `tech-decisions.md` 与拍板一致
- [ ] ADR 已逐条判定，命中的已写入 `docs/adr/`
- [ ] 已回到并继续 plan
