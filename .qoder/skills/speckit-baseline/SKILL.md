# Speckit Baseline Skill

# 存量项目 Baseline

生成 `docs/spec-baseline.md`：一张帮助后续 Change 找到现有代码、流程和文档的索引。它是导航，不是完整系统规格，也不是新的门禁。

## 1. 有界探测

先读顶层结构和现有文档入口，再沿证据找必要文件：

- 依赖清单、锁文件、构建与测试配置、CI 配置。
- README、CONTRIBUTING、docs/ 的索引或相关文档。
- 主要源码入口、模块边界和已有测试入口；只深入足以定位主要职责的层级。
- `specs/` 仅登记目录位置；当前指针只读 `.specify/feature.json`。证据取源码、构建/测试/CI 配置和非 specs 文档，不打开 `specs/**` 文件；仅见于其中的命令或约束写“未知”。

每条结论标注为“已观察 / 推断 / 未知”，并给出来源路径。已观察指直接读到文件或配置；推断必须写出依据；证据不足写未知。现有文档已经说明的内容只保留指针和一句定位，不复制正文。

只记录命令、路径和非机密配置含义，不复制凭据、令牌、连接串或环境变量的值。探测阶段不安装依赖，不运行构建、测试、发布或应用代码。

判据：项目地图中的每个主要入口都有来源；没有把“可能如此”写成已观察事实，也没有为穷举而遍历全库。

## 2. 写入单文件基准

未发现源码、依赖配置或现有文档等存量证据时，报告“未探测到存量项目”，不创建空 baseline。否则创建 `docs/spec-baseline.md`，按实际证据填写以下结构；没有相关证据的小节写“未知”，不编造内容：

```markdown
# Project Baseline

> 探测日期：<YYYY-MM-DD>
> 本文件是按需阅读索引，不是当前系统完整规格。

## 项目地图
| 区域 | 主要职责 | 入口 / 源码 | 证据 |
|---|---|---|---|

## 现有流程与文档
| 事项 | 流程或命令 | 来源 | 状态 |
|---|---|---|---|

## 已文档化约束
- <约束摘要> — <来源路径；只收项目已经声明的规则>

## 验证入口
| 目的 | 命令或入口 | 来源 | 执行情况 |
|---|---|---|---|

## 按需阅读索引
| 当变更涉及 | 再读 | 原因 |
|---|---|---|

## Change 流程
- Change 历史位于 `specs/`；它不是当前系统完整规格。
- 新变更使用 `/speckit-change start`；按需读取本文件相关小节，不全量加载。

## 人工补充
<保留用户补充；初始没有则写“无”>
```

“验证入口”的命令若只从配置读到，执行情况写“未执行”；只有本会话实际运行并取得结果时才写命令结果。流程和文档索引应覆盖开发、构建、测试、发布中实际存在的部分，不替项目补造流程。

判据：文件只含一个导航层；后续 agent 能根据“当变更涉及”找到下一篇该读的文档，而不是把 baseline 当作全部上下文。

## 3. 重跑与更新

- 已有 baseline 时先读取并重新核对证据；无实质变化则保持文件字节不变。
- 有变化时先列出将新增、修正或删除的条目，等待用户确认后再更新。
- 更新时完整保留 `## 人工补充`，不把其中的内容当作探测事实覆盖；用户明确要求修订该节时才按用户输入处理。
- 不自动修改 constitution、ADR、GLOSSARY、历史 Change 或应用源码；这些仍走各自命令与确认规则。

判据：重复运行不会制造格式差异，用户补充和既有治理文档不会被探测结果静默覆盖。

## 完成报告

报告 baseline 路径、主要证据来源、未知项和未执行的验证命令，并提示下一步可使用 `/speckit-change start <变更描述>`。不自动启动 Change。
